# Deploying GWD Club OS on Render

One Render web service runs the API **and** serves the website. That is
deliberate: on web the app resolves its API base to the origin it was served
from, so a single origin means no CORS setup and no second URL to keep in sync.

Total time: about 20 minutes, most of it waiting for the first build.

---

## 1. The database — MongoDB Atlas

Render has no managed MongoDB, so the database lives at Atlas.

**This is not a free choice of provider: the database must be a replica set.**
Change Streams are built on the oplog, and a standalone `mongod` does not have
one — live sync would silently do nothing while everything looked fine. Atlas's
free M0 tier *is* a three-node replica set, so it works.

1. Sign up at [mongodb.com/cloud/atlas](https://www.mongodb.com/cloud/atlas) and
   create a free **M0** cluster. Pick the region nearest your users (Mumbai
   `ap-south-1` for India).
2. **Database Access** → Add New Database User. Username and a generated
   password. Role: *Read and write to any database*. Copy the password now; it
   is not shown again.
3. **Network Access** → Add IP Address → **Allow access from anywhere**
   (`0.0.0.0/0`).

   Render's free plan does not give your service a fixed outbound IP, so there
   is nothing narrower to allow. The database is still protected by the user
   password and TLS — but it does mean that password is the only thing standing
   in front of it, so let Atlas generate a long one.
4. **Connect** → *Drivers* → copy the connection string. It looks like:

   ```
   mongodb+srv://gwd:<password>@cluster0.abcde.mongodb.net/?retryWrites=true&w=majority
   ```

   Replace `<password>` with the real one. If it contains `@`, `/`, `:` or `#`,
   URL-encode those characters or the string will not parse.

## 2. The service — Render

The repo already contains `render.yaml`, so Render can create everything itself.

1. [dashboard.render.com](https://dashboard.render.com) → **New** → **Blueprint**.
2. Connect GitHub and pick **`abdulmudabbirofficial/GWD-CLUB-OS`**.
3. Render reads `render.yaml` and proposes a service called `gwd-club-os`.
4. It will ask for the variables marked `sync: false`. Fill them in:

| Variable | What to put | Why it is not in the repo |
|---|---|---|
| `MONGODB_URI` | the Atlas string from step 1 | contains the database password |
| `SEED_DIRECTORS` | `Name:email:password,Name2:email2:password2` | real passwords |
| `SEED_FACULTY` | `Name:faculty@…:password` | real password |
| `SEED_PRESIDENT` | `Name:president@…:password` | real password |
| `CLIENT_ORIGIN` | your Render URL, e.g. `https://gwd-club-os.onrender.com` | differs per deploy |
| `PORT` | **leave blank** — Render sets it | — |

`JWT_SECRET` is generated by Render automatically. You never see it and never
need to.

> **Use real names in the seed variables**, not job titles. `Asha Rao:director1@gwd.club:…`,
> not `Director One:…`. The app treats a seeded name as provisional and asks the
> holder to confirm it on first sign-in, but starting from a real name is better.

5. **Apply**. The first build takes 8–12 minutes: it installs the API's
   dependencies, then clones the Flutter SDK and builds the web app.

## 3. Check it worked

```bash
curl https://<your-service>.onrender.com/api/health
```

You want:

```json
{"service":"GWD Club OS API","status":"online","mongo":"up","changeStreams":true,...}
```

The one to actually read is **`changeStreams`**. If it is `false`, Mongo
connected but is not a replica set, and live sync is dead — go back to step 1
rather than shipping it.

Then open `https://<your-service>.onrender.com` in a browser. You should get the
sign-in screen, and the seeded President should be able to sign in.

Render's deploy log prints the six department Lead passwords **once**, at first
startup. Copy them out of that log — they are hashed and there is no second
chance. If you miss them, a Director can reset each one from the member
directory.

## 4. Point the phone app at it

Render appends a random suffix when the service name is taken, so the real URL
is usually **not** `https://gwd-club-os.onrender.com`. Take the one the
dashboard shows — e.g. `https://gwd-club-os-abrw.onrender.com` — and go back and
correct `CLIENT_ORIGIN` to match it.

The APK has its address compiled in, so it needs rebuilding once:

```powershell
.\scripts\build-apk.ps1 -BaseUrl https://gwd-club-os-abrw.onrender.com
```

Use `-BaseUrl`, not `-Ip`. `-Ip` is for a server on the LAN and produces
`http://host:4000` — wrong scheme and a port Render does not serve.

By hand, if you prefer:

```powershell
cd app
flutter build apk --release --split-per-abi `
  --dart-define=GWD_API_BASE=https://gwd-club-os-abrw.onrender.com
```

Note **`https`**. Once the backend is behind Render's TLS you can also tighten
two things that only existed for the plain-HTTP LAN server:

- `app/android/app/src/main/res/xml/network_security_config.xml` →
  `cleartextTrafficPermitted="false"`
- `app/ios/Runner/Info.plist` → drop the `NSAppTransportSecurity` block

Anyone already holding an older APK does not need a new one: the sign-in screen
has a server-address override. Paste the Render URL there.

## What the free plan costs you

Three real limitations. None is a bug, and all three are worth knowing before
the club relies on this.

**The service sleeps after 15 minutes of no traffic.** The next request wakes it
and takes 30–60 seconds. To a member that looks like the app hanging on sign-in.
A paid instance ($7/month) never sleeps.

**Uploaded files do not survive a deploy.** Render's free filesystem is
ephemeral, so permission letters and expense receipts are wiped every time you
push. Two ways round it:

- Add documents as **links** (Drive, etc.) rather than uploads — those are just
  URLs in the database and are unaffected. The upload sheet already supports it.
- Or move to `plan: starter` and uncomment the `disk:` block in `render.yaml`,
  then set `UPLOAD_DIR=/var/data/uploads`.

The API refuses uploads with a clear message when storage is unavailable rather
than failing to boot, so this degrades rather than breaking.

**The daily reminder sweep needs the service awake.** It ticks hourly from
`REMINDER_HOUR` (set to `3`, which is 09:00 IST since Render runs in UTC). A
sleeping instance has no timer running, so on the free plan reminders fire
whenever the service next wakes — late rather than never, which is the tradeoff
the sweep was written for. A paid instance makes it reliable.

## When something is wrong

| Symptom | Cause |
|---|---|
| Build fails on `render-build.sh: permission denied` | the executable bit was lost; `git update-index --chmod=+x render-build.sh` |
| Build fails on `bad interpreter: ...^M` | CRLF line endings; `.gitattributes` pins `*.sh` to LF |
| `status: degraded`, `mongo: down` | `MONGODB_URI` wrong, or Atlas Network Access does not allow `0.0.0.0/0` |
| `changeStreams: false` | the cluster is not a replica set |
| Site loads but sign-in fails | check `CLIENT_ORIGIN`, and that the Render URL is what the app is pointed at |
| Blank white page | the web build did not run — check the build log for the Flutter step |
| Everyone signed out after a deploy | `JWT_SECRET` changed; never edit it once set |

Logs are under the service → **Logs**. Startup prints Mongo state, whether
Change Streams are live, and whether push is configured.
